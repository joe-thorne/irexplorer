# Study API contract

At startup, the service loads the installed public `participant-package-v2.json` and its `public-manifest.json` from the evaluation package directory. It checks the exact package-byte hash, schema and manifest keys, identity/version tuple, canonical public digest, and closed nested public-content schema before exposing content. The runtime does not read thesis source, YAML, or compiler output. The verified package is cached for the process lifetime; `GET /api/study/content` returns its participant-facing content through an explicit allowlist, with server-configured collection status. It includes information, consent, question types/options/scales, task instructions, and workspace defaults and metadata. Researcher mappings and expected answers are not served. The compiler's legacy participant-content JSON remains a separate compatibility artifact.

`POST /api/study/submissions` accepts the final JSON submission from the configured exact origin. Collection mode, origin, content type, body size, and strict JSON parsing are checked first for every request. The service then looks up the submission ID; if it is already committed, the request is a retry and is answered from the stored record without current-instrument validation (below). Otherwise it resolves the submission's study, content, and instrument identities to an accepted instrument release, then validates consent, field types and bounds, task completion/order, and identifiers before storage. Section and task membership comes from the package's explicit membership table and is checked against each declared section and field owner; field identifier prefixes do not determine membership. It validates against that release's own package, not the installed one. It commits the complete response, linked to that release's participant-content snapshot, transactionally before returning a receipt. The installed package is always accepted. An earlier release is accepted only when its frozen public pair is configured on the server (see [accepted instrument releases](evaluation-operations.md#accepted-instrument-releases)). Submitted JSON cannot register one.

- First accepted submission: `201`.
- Identical retry with the same submission ID: `200`, with the original receipt.
- Conflicting reuse of that ID: `409`, without disclosing stored responses.
- First delivery naming identities that are not an accepted instrument release: `422` with code `unsupported_instrument`. Nothing is stored. The message is the one used for `invalid_submission`; the code lets the browser report incompatibility rather than an uncertain delivery.

A retry is identical when it names the stored instrument, content, and study versions and its canonical form has the stored digest. The canonical form is computed under the stored row's own `canonicalVersion` (currently only version 1: sorted-key compact UTF-8 JSON with multi-choice codes sorted), not under the installed package's rules. A committed submission therefore recovers its original receipt after an application or package upgrade, including records stored before participant-content snapshots. Changed answers or identities under that ID, or a stored contract the server does not know, return `409`; the saved record is unchanged. This is distinct from a first delivery of an uncommitted draft from an older release, which is rejected with `422 unsupported_instrument` unless that release is accepted, and is then validated against its own rules.

The browser freezes the submission before sending and retries that same submission after uncertain delivery. No draft is sent on unload. Compiler queries remain read-only and cannot invoke compilation or mutate study records.

See [study operations](evaluation-operations.md) for modes, data paths, and private researcher commands, and the runtime `/docs` endpoint for HTTP schemas.

## Instrument v0.11 preview 2

The installed preview package uses instrument `v0.11`, content `v0.11-preview-2`, and study `v0.11-synthetic-1`. The package's version tuple and canonical identity are included in release metadata and the content endpoint. Old drafts are incompatible unless their release is deliberately accepted. They require explicit discard/restart. Historical stored responses are not rewritten.

Each submitted task includes `id`, `status`, `durationMs`, `interrupted`, and `answers`; `setupReached` is not collected. Completing, skipping, or reporting inability does not depend on reaching the requested comparison, and partial answers and elapsed duration can be retained. `durationMs` starts at task presentation and counts visible time, excluding hidden-tab time, explicit pauses, and reload downtime. Keep it separate from v0.5/v0.6 post-setup duration. Release metadata uses submitted JSON schema version 2; the SQLite submission-store schema is version 3. Status codes, request bounds, origin checks, receipt shape, and conflict responses are unchanged. The one addition is the `unsupported_instrument` error code on the existing `422` status. No request, receipt, recovery-record, or package field changed, so the submitted JSON schema (2), recovery key (`irexplorer.submission.v3`), and package schema (2) keep their versions. The server links each new submission to the participant-content snapshot of the accepted instrument release it was validated against, in the same transaction as the insert; a snapshot integrity failure returns `503 storage_unavailable` without a receipt.

Field definitions returned by the content endpoint are authoritative. Presentation control hints (`radio`, `checkbox`, `checkboxes`, `select`, `textarea`, and `input`) guide the browser renderer without changing response meaning. Private exports take codebook definitions from each record's stored participant-content snapshot, never from the content currently served; records without a snapshot are marked unavailable.

Journey wording also comes from the content endpoint: section introductions (`journey.introductions`), T0 glossary help (`glossary`), and the compiled `messages` catalogue for progression, locking, timing, storage, discard, review, submission, receipt, recovery, and cleanup guidance. The browser chooses each message key and validates, before using the content, that every key it displays is present with exactly its compiled placeholders. Content failing that check is treated as unavailable, like an unsupported version. Messages are displayed as text, never markup. Routes, guards, timing, transport, and accessibility structure remain application code. Only the loading and content-unavailable wording is bundled with the browser, because no verified catalogue exists then; the study draft check keeps it identical to the packaged catalogue.
